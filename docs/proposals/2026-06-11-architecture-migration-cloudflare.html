1. Contexto y Estado Actual

El sistema actual está distribuido entre tres proveedores diferentes (Vercel, Supabase y Railway), lo que incrementa la latencia y los costos de infraestructura.

Arquitectura Actual (Multicloud)
Arquitectura Target (Cloudflare Edge)

El objetivo es migrar hacia Cloudflare para ganar en velocidad en el edge, unificar el lenguaje de desarrollo a TypeScript puro y reducir la sobrecarga de mantenimiento.

2. Análisis de Tradeoffs & Riesgos Críticos

⚠️

Pérdida de Row-Level Security (RLS) en D1

Supabase PostgreSQL provee RLS a nivel de motor de base de datos. Cloudflare D1 usa SQLite, que no cuenta con esta capacidad. Al migrar a D1, toda la lógica de autorización debe ser implementada en la aplicación (Astro/Workers), lo cual aumenta el riesgo de fugas de datos involuntarias si no somos sumamente disciplinados con las consultas SQL.

⚙️

Cambio de Motor: PostgreSQL a SQLite

Perdemos tipos de datos nativos como arrays (TEXT[]), JSONB indexado por GIN y triggers complejos. Tendremos que parsear los JSON en el código de aplicación y adaptar las consultas jerárquicas de ubicaciones.

💡

Eliminación del Backend de Python

Actualmente, FastAPI en Railway procesa llamadas a Claude Vision y genera imágenes de etiquetas QR con Pillow. Migrar esto a TypeScript en Workers elimina Railway por completo y unifica nuestra base de código en un solo lenguaje.

3. Plan de Adopción por Fases

Para realizar la transición sin disrupción, utilizaremos un enfoque por fases completamente independientes y commiteables:

Hosting Frontend en el Edge Fase 1

Adaptación del frontend Astro usando el adaptador oficial de Cloudflare y despliegue inicial en Cloudflare Pages. El backend, la autenticación y la base de datos se mantienen en Supabase de forma transparente.

Remoción del Microservicio de Python Fase 2

Migración de endpoints de FastAPI a rutas API de Astro. La generación de etiquetas QR se realiza mediante canvas de JS en el Worker. Reemplazo de llamadas directas a OpenAI/Anthropic desde el Edge.

Migración de Almacenamiento a R2 Fase 3

Creación de un bucket R2 y configuración de un cliente compatible con el SDK S3. Script para migrar los archivos binarios existentes desde Supabase Storage.

Migración de Base de Datos y Autenticación Fase 4

Traducción del schema Postgres a SQLite para D1. Migración de usuarios a base de datos D1 con Lucia Auth. Paso Crítico: Implementación de políticas de filtrado manual de seguridad a nivel de métodos CRUD en src/lib/.

4. Preguntas Abiertas & Decisiones del Equipo

  • ¿Es viable evitar D1 para mantener Postgres RLS?
    Podríamos usar Cloudflare Pages para frontend e IA, y Cloudflare Hyperdrive para conectar a Supabase Postgres de forma segura. ¿Vale la pena el esfuerzo de migrar a SQLite a costa de perder RLS?
  • ¿Cómo validaremos la seguridad sin RLS?
    Si procedemos con D1, será mandatorio implementar tests de integración rigurosos para cada método de negocio que aseguren la separación de datos por usuario.
  • ¿Workers AI vs APIs de Terceros?
    ¿Reemplazamos Claude Vision por modelos de código abierto locales en Workers AI, o mantenemos llamadas HTTP externas para el reconocimiento de componentes electrónicos complejos?
