1. Contexto y Estado Actual

El sistema actual está distribuido entre tres proveedores diferentes (Vercel, Supabase y Railway), lo que incrementa la latencia de red en las consultas del BFF y los costos de mantenimiento de múltiples infraestructuras.

2. Análisis de Tradeoffs & Riesgos Críticos

⚠️

Pérdida de Row-Level Security (RLS) en D1 (SQLite)

Supabase PostgreSQL provee RLS a nivel de motor de base de datos. Cloudflare D1 usa SQLite, que no cuenta con esta capacidad. Al migrar a D1, toda la lógica de autorización debe ser implementada en la aplicación (Astro/Workers), lo cual aumenta el riesgo de fugas de datos si no somos sumamente disciplinados con las consultas SQL.

⚙️

Cambio de Motor: PostgreSQL a SQLite

Perdemos tipos de datos nativos como arrays (TEXT[]), JSONB indexado por GIN y triggers complejos. Tendremos que parsear los JSON en el código de aplicación y adaptar las consultas jerárquicas de ubicaciones.

Análisis de Cloudflare Workers AI

La integración de modelos de lenguaje e imágenes nativos de Cloudflare elimina la necesidad de conectarse a servidores de IA intermedios, pero introduce fricciones de capacidad técnica:

Fricciones y Limitaciones
  • Ventana de Contexto: Modelos integrados (Llama 3 8B, Mistral 7B) limitan la entrada a 8k-32k tokens. Para planificar BOMs complejos o analizar firmwares embebidos extensos, la ventana se queda corta frente a los 200k de Claude 3.5.
  • Modelo de Visión Inexacto: El reconocimiento de componentes requiere identificar textos grabados diminutos. Los modelos de visión nativos en el edge (como Llama-3.2-Vision) muestran tasas de error muy superiores a Claude 3.5 Sonnet o GPT-4o.
  • Cold Starts de GPUs: Los Workers AI pueden experimentar latencias variables si las GPUs del nodo de Cloudflare están cargadas.
Costos y Competidores
  • Costos (Workers AI): Facturado en "Neuronas". Capa gratuita de 10,000 neuronas diarias. Superado ese límite, el costo es de ~$0.01 a $0.07 por millón de tokens. Es extremadamente barato.
  • Competidor Groq: Velocidad ultrarápida (LPUs), pero requiere una llamada de red externa (aumenta latencia total y depende de terceros).
  • Competidor Replicate/RunPod: Servidores GPU dedicados bajo demanda. Ideales para fine-tuning, pero costosos para tráfico irregular y con altos cold starts de contenedores.
  • APIs de Frontera (OpenAI/Anthropic): Máxima inteligencia y capacidad de visión, costo elevado y latencia de red variable.

3. Escenarios de Arquitectura Híbrida

En lugar de una migración del 100%, existen escenarios intermedios que minimizan el esfuerzo de desarrollo y maximizan la confiabilidad del sistema:

Escenario A: Almacenamiento e IA Híbridos
Riesgo Bajo

El frontend Astro se migra a Cloudflare Pages. La base de datos, la autenticación y el RLS permanecen en Supabase Cloud de forma nativa. Las fotos del inventario y planos de proyectos se mueven a Cloudflare R2 para eliminar costos de transferencia. La API de Python en Railway se elimina y se conecta directo con las APIs de OpenAI/Anthropic desde el edge.

Velocidad Acceso
🟢 Alta (Edge Frontend)
Simplicidad Admin
🟢 Alta (Preserva Supabase)
Ahorro Costo
🟡 Medio (R2 egress $0)
Escenario B: Híbrido Optimizado con Hyperdrive
Riesgo Medio

Aprovecha la infraestructura de Cloudflare Pages para el Frontend y Cloudflare R2 para archivos. La base de datos sigue en Supabase Postgres con RLS y Auth activo. Se introduce **Cloudflare Hyperdrive** en el medio para mantener un pool de conexiones abierto y cachear consultas SQL frecuentes directamente en el edge.

Velocidad Acceso
⚡ Máxima (DB en el Edge)
Simplicidad Admin
🟢 Alta (Preserva Postgres RLS)
Ahorro Costo
🟢 Alto (R2 + Hyperdrive)
Escenario C: 100% Cloudflare Nativo
Riesgo Muy Alto

Migración absoluta. Se traduce la base de datos a SQLite sobre Cloudflare D1. La autenticación se implementa con Lucia Auth en tablas de D1. Todo el contenido estático y archivos va a R2. La lógica de IA corre sobre Workers AI con llamadas de soporte externo. La lógica de RLS se implementa en JS/TS a nivel de código de aplicación.

Velocidad Acceso
⚡ Máxima (Mismo DataCenter)

🟢 Máximo (D1/R2 sin cargo fijo)

5. Plan de Adopción por Fases (Escenario B Recomendado)

El camino más balanceado es el **Escenario B**. Permite ganar velocidad en la capa de datos y ahorrar costos de almacenamiento sin comprometer el modelo de seguridad estructurado:

Hosting Frontend y Storage R2 Fase 1

Adaptación del frontend Astro usando el adaptador de Cloudflare y despliegue inicial en Cloudflare Pages. Migración del almacenamiento de imágenes a R2 mediante la SDK compatible de S3.

Optimización de Base de Datos con Hyperdrive Fase 2

Configuración del túnel de **Cloudflare Hyperdrive** hacia la base de datos de Supabase PostgreSQL. Caching de lectura activo en el Edge para reducir el tiempo de respuesta de consultas comunes.

Remoción de Railway (Lógica de IA y QR en Workers) Fase 3

Eliminación del microservicio de Python. Reescritura del generador de QR usando JS canvas y migración de peticiones del modelo Claude a llamadas directas seguras desde Cloudflare Workers.

6. Preguntas Abiertas & Decisiones del Equipo

  • ¿Estamos conformes con la latencia adicional en escrituras?
    En los escenarios A y B, las escrituras siguen viajando hasta Supabase PostgreSQL. Hyperdrive acelera enormemente las lecturas repetidas, pero las escrituras tienen la penalización física de red de ~20-30ms. Para este tipo de aplicación (CRUD de inventario), esto suele ser imperceptible para el usuario.
  • ¿Qué tareas IA podemos descargar a Workers AI?
    Si bien el reconocimiento óptico de componentes exige modelos grandes (como Claude), la generación de código base simple o la estructuración de texto puede derivarse a modelos de texto en Workers AI para ahorrar costos de tokens en un 95%.
  • ¿Con qué modelo de Auth nos sentimos más cómodos para el largo plazo?
    Si decidimos ir al Escenario C, migrar a Lucia Auth sobre D1 nos da control absoluto sobre los tokens de sesión, pero nos obliga a crear vistas administrativas a mano que Supabase Auth nos regala de fábrica.
